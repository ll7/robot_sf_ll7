# Development config seed audit

Actual training identities and training control master seeds use 100000–199999.
Selection uses 1031–1060; development evaluation uses 1101–1130. Optuna's CLI
seed is a sampler/control seed, not a PPO episode seed; its master now uses the
training range as requested, while the separate PPO reset list is also migrated.
Authored selection fields retain their selection role. Active training manifests
and script fallbacks are covered, including predictive collection and shuffle
seeds. `train_ppo.py` remains owned by the separate seed-policy lane.

Migration changes experiment identity. Prior outcomes, checkpoint selections and
failure labels do not transfer. Lists preserve order and cardinality; whole-range
migration replaces unrestricted entries too. In particular, five original
`range(101, 113)` sites became `range(1101, 1113)`, preserving twelve seeds while
also replacing 101–110. The training-pool correction similarly moves older seeds
outside the approved training pool, not just restricted-band literals. Step
counts, timestep budgets, IDs and seed counts are not migrated.

`configs/benchmarks/dev_seed_sets.yaml` and `dev_seed_list.yaml` are development
transports. `dev_eval_sN` tier names differ from protected paper schedules and
confer no release authority. Training-only predictive manifests preserve list
sizes while changing seed identity; their historical hard-case outcomes do not
transfer. Frozen consumers retain their original source bytes and transports.

The CV forecast evaluator reads historical traces without executing episodes.
Its published seed comes from each artifact's `source.seed`; candidate metadata
cannot relabel that identity. The three DWA diagnostic exporters carry explicit
seed-migration metadata and mark prior outcome descriptions as superseded. Legacy
episode IDs remain compatibility labels. Rescue reports withhold paired deltas
when scenario/seed identity differs from the archived baseline. No replacement
trace was generated by this migration.

`tests/validation/test_active_config_seeds.py` scans active YAML seed literals,
quoted lists, aliases, integer encodings and CLI arguments. Its role predicate
checks numeric training, selection and evaluation fields separately. Its Python
AST scan covers the audited script inventory plus every independently owned
training script. It checks assignments, dictionaries, function/CLI defaults,
get fallbacks, diagnostic tuple seed columns and bounded range contents. It
skips arithmetic seed offsets and explicitly marked provenance-only identities.
Dynamic generation and environment overrides still require runtime admission.
Diagnostics show file, line, field and `<seed>`.

The exclusion inventory pins exact frozen/versioned release paths, transitive
dependencies, frozen preregistrations, registered historical campaign inputs and
pre-refactor resolved-config baselines by original hash. Historical inherited
parents are traversed even when the leaf itself did not change.
The regression verifies those bytes remain unchanged. CI digest failures identified additional historical contracts and source
companions; those inputs were restored to origin/main bytes and their existing
registered digests retained. Live tests now assert development identities, while
historical digest and resolved-baseline assertions remain unchanged.

Run focused static proof without importing or stepping the simulation stack:

```bash
scripts/dev/run_worktree_shared_venv.sh --standalone -- uv run python -m pytest tests/validation/test_active_config_seeds.py tests/validation/test_seed_audit_trace_metadata.py --confcutdir=tests/validation -o addopts='' -q
```

This is configuration and provenance integrity proof, not training, planner
performance, hosted CI or release-admission evidence.

The live Optuna launcher resolves `dev_expert_ppo.yaml`, a training-only copy.
The historical `expert_ppo.yaml` reset identities and recipe digests stay unchanged.
A regression checks the resolved live reset list against the approved training
pool after the historical archive is restored.

Historical preservation also covers the retrospective component-ablation manifest,
the executed one-factor manifest and the recorded predictive paired schedule and
its four row recipes. The protected predictive contract's declared config inputs
are traversed transitively and pinned, including the planner grid and hard-seed
transport. Its original rows and previously reported negative outcomes remain
unchanged.

The executable one-factor pilot defaults to
`dev_one_factor_hybrid_component_manifest.yaml`. The predictive training CLI
routes the four archived paired recipe paths to explicitly named `dev_` successors;
those successors use a separate training-only base seed manifest and distinct run
and model identities. Existing historical paths remain available for provenance
inspection. Development copies confer no authority on archived outcomes.
